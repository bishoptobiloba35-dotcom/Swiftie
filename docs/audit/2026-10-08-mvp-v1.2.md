# SwiftDrop MVP v1.2 Audit — 2026-10-08

## Scope
This audit reconciles the uploaded MVP v1.2 delivery-types/payment specification against the current main branch of bishoptobiloba35-dotcom/Swiftie. It is an implementation audit, not a prototype plan.

## Executive finding
The current production branch is materially hardened around sender-funded escrow, but it does not yet implement the v1.2 two-mode contract. Migration 076 currently permits only SENDER_ESCROW, while v1.2 requires exactly SENDER_ESCROW and RECEIVER_ESCROW. PR #240 attempted to remove the retired legacy type but would have made that conflict permanent; it was therefore closed unmerged.

## Payment contract
- Existing/verified: Paystack escrow infrastructure, webhook reconciliation, DVA/bank-transfer provisioning, idempotent escrow attempts, float ledger, payout reconciliation.
- Partial: escrow_payment_attempts has method, amount, status, reference and idempotency key, but no payer role/collection channel.
- Missing: active RECEIVER_ESCROW order mode; receiver deposit; receiver goods amount; receiver user linkage; server-side payer-specific expected amount.
- Retired value still present: RECEIVER_ON_DELIVERY appears in historical migrations, compatibility tests and repository code. It must remain only as a migration/test rejection target, never an accepted production value.
- Cash: active payment-method list is provider-based and contains no cash method, but old UI/rule text still contains payment-on-delivery language and must be cleaned.

## Delivery types
- Partial: existing drop-off/station network tables exist (drop_off_locations, drop_off_parcels, drop_off_events).
- Missing: an authoritative delivery-type field and server-enforced EXPRESS versus STANDARD behavior; station handover/payment/collection lifecycle for the v1.2 pilot.
- Out-of-scope conflicts: broader production surfaces for marketplace, errand, business and AI exist and must be disabled behind production-off flags for v1.2, not deleted.

## Lifecycle
- Existing/partial: delivery state machine, event recording, pickup/evidence, PIN confirmation, escrow dispute/release infrastructure.
- Missing: distinct receiver-payment states and station states with server-authoritative transitions.
- Verified constraint: PIN confirmation is a settlement/confirmation boundary in current escrow tests, but payer-specific funding and handover guards are incomplete.

## Receiver identity and access
- Existing: receiver phone is stored and used for tracking/notifications.
- Missing: nullable receiver_user_id, verified-phone binding and a receiver-scoped order view exposing only the v1.2 permitted fields.

## PIN
- Partial: four-digit PIN and lock-related fields/tests exist; v1.2 still requires verification of HMAC scheme, atomic attempt increments, lock schedule, secret validation and log scrubbing.
- Risk: current repository exposes a receiver PIN input in create-delivery APIs; v1.2 requires server generation and SMS delivery only.

## Evidence
- Existing/verified: pickup proof and private evidence infrastructure; perishable proof hardening was merged.
- Missing: universal receiver-pays handover photo+GPS requirement and explicit GPS mismatch enforcement for all receiver-pays orders.

## Assignment/tracking/geofence
- Partial: courier assignment, driver verification, evidence and tracking infrastructure exist.
- Missing/needs audit: v1.2 corridor/geofence fail-closed enforcement, stale-location UX and pilot background-location requirements.

## Payouts/wallets
- Existing/partial: stakeholder wallets, minimum withdrawal, Paystack Transfers and reconciliation exist.
- Missing: sender goods-money balance for receiver-pays settlement and v1.2 two-person approval enforcement.

## Phase 2 feature flags
- Missing as a complete v1.2 gate: one server-side production-off flag per out-of-scope module with API/database/RLS refusal tests.

## Legal gates
docs/legal-gates.md did not exist on current main and must be created before claiming M0 completion.

## CI / PR classification
- PR #240 CI run #1917 passed, but the PR implemented the wrong product contract for v1.2 and was closed unmerged.
- Current readiness remains 76%; this audit does not increase it.

## Next implementation gate
M0/M2 foundation work: establish the two-mode database contract, v1.2 delivery type contract, payer metadata, server-side feature flags/legal gates, and regression tests. Do not enable receiver-pays production settlement until the licensed escrow-partner gate is green.
